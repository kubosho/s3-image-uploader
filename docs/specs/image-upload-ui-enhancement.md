# 画像アップロードUIのリッチ化と状況表示の改善

## 目的

画像アップロードのUIを Google Drive / Dropbox 並みに分かりやすくする。

- ギャラリー領域のどこにでもドラッグ&ドロップできてアップロードできる
- アップロードファイルのサムネイル付き一覧
- ファイル単位のアップロード状況表示
- 全体進捗サマリ
- 失敗ファイルの再試行

これらの機能を提供することでアップロード中に「今どのファイルがどうなっているか」をユーザーが一目で把握できる状態にする。

## 現状

- `ImageUploadButton` は ark-ui の `FileUpload` を使うが `allowDrop={false}` でドラッグ&ドロップは無効。アップロードはボタン経由のみ
- `useImageUploader` は `status`（`idle` / `uploading` / `success` / `error`）と `error` を返すが、`ImageUploadButton` はこれらを一切使っておらず、UI上に状況表示が存在しない
- アップロードは `Promise.all(files.map(uploadSingleImage))` で全ファイルを一括並列実行しており、ファイル単位の状態という概念がない
- アップロード完了/失敗後 3 秒で状態がリセットされる
- API Route (`src/app/api/images/upload/route.ts`) は 1 リクエスト 1 ファイルを受け取り `imagePath` を返す
- `page.tsx` には `FileUpload.Root` が 2 つある。1 つは `ImageUploadButton` 内（アップロードつなぎ込みあり）、もう 1 つは `Images` を包む `FileUpload.Root`（`HiddenInput` のみで、アップロードつなぎ込みなし・ドロップ未処理の状態）。後者はファイルアップロードに何も寄与していない
- 既存のローディング表現として、スケルトン (`DummyImages`) と `aria-live` 読み上げ (`ImagesLoadingAnnouncer`) のパターンがある

## 受け入れ基準

### AC-1：アップロード状態をファイル単位で保持する

複数ファイルを渡してアップロードを開始すると、各ファイルが `queued` → `uploading` → `success` または `error` と個別に状態遷移し、`useImageUploader` がファイルごとの状態を持つリストを返す → あるファイルが失敗しても、他のファイルの状態は独立して `success` まで進む（1件の失敗が全体を巻き込まない）。

### AC-2 (Depends On：AC-1)：ファイル単位の状況リストを表示する

ファイルをアップロードすると、各ファイルのファイル名と状態バッジ（待機中 / アップロード中 / 完了 / 失敗）が一覧で表示される → 状態遷移に追従してバッジの表記が切り替わる。

### AC-3 (Depends On：AC-2)：各ファイルにサムネイルを表示する

状況リストの各行に、アップロードした画像のサムネイルが表示される → ファイル名・状態バッジとあわせて、どの画像かを視覚的に判別できる。

### AC-4 (Depends On：AC-1)：全体の進捗サマリを表示する

アップロード中、「N件中M件完了（失敗K件）」形式の全体サマリが表示される → 状態更新に追従して件数が変わり、`aria-live`（既存 `ImagesLoadingAnnouncer` 準拠）で読み上げられる。

### AC-5：ギャラリー領域のどこにドロップしてもアップロードできる

アップロードボタンとギャラリーを含むコンテンツ領域全体がドロップゾーンになり、領域内のどこにファイルをドラッグしても領域全体がハイライトされ、ドロップするとアップロードが開始する → 従来のトリガーボタン経由のアップロードも引き続き使える。`page.tsx` の 2 つの `FileUpload.Root` は 1 つに統合し、ボタン・状況表示・ギャラリーが同一の受理ファイル状態を共有する。

### AC-6 (Depends On：AC-1, AC-2)：失敗ファイルを再試行できる

`error` 状態のファイル行に再試行ボタンが表示され、押すとそのファイルだけ再アップロードされる → 状態が `queued` → `uploading` → `success` / `error` と再遷移する。

## ネガティブ要件

- 実バイト進捗（%）やプログレスバーは実装しない。状態（待機中 / アップロード中 / 完了 / 失敗）のみ表示する
- 進捗 % を取るための XHR / `fetch` + `ReadableStream` への書き換えはしない。既存の `fetch(body: file)` 方式を維持する
- 複数ファイルを並列でアップロードする既存挙動を維持する。直列化しない
- アップロードの自動リトライはしない。再試行は失敗ファイルの手動ボタンのみ
- アップロードのキャンセル機能は実装しない（今回のスコープ外）
- 画像の編集・リサイズ・クロップ・回転は対象外
- API Route (`src/app/api/images/upload/route.ts`) のレスポンス契約とサーバー側挙動は変更しない（1 リクエスト 1 ファイルのまま）
- 削除機能 (`TrashButton`) と S3 側の挙動は変更しない
- ドロップアップロードはコンテンツ領域（アップロードボタン＋ギャラリー）内に限る。`SiteHeader` や認証前の画面など、コンテンツ領域外への全画面ドロップは対象外

## スコープ上限

想定変更量は 10 ファイル前後、総行数の目安は 500 行以内。これを大きく超えたら軸Cで超過候補として扱う。`FileUpload.Root` の統合に伴い `page.tsx` と、ボタン・状況表示・ギャラリーを束ねるクライアントコンポーネントの新設が含まれる。

## 技術的制約

- ドラッグ&ドロップ・サムネイル・ファイル一覧は ark-ui `FileUpload` のパーツ（`Dropzone`、`ItemGroup`、`Item`、`ItemPreviewImage`、`ItemName` など）を土台にし、自前の DnD / プレビュー実装は追加しない。自前実装はファイル単位のアップロード状態管理に限る
- ark-ui `FileUpload` は `maxFiles > 1`（本プロジェクトは `maxFiles=100`）のとき内部 `acceptedFiles` に新規ファイルを累積追記し、`onFileAccept` は累積全体を渡す（`@zag-js/file-upload` の `setEventFiles` / bindable `onChange`）。完了後にローカル state だけクリアすると ark-ui 内部のリストは残り、次回アップロード時に完了済みファイルが再アップロードされる。状況リストの表示元と完了後のクリアはこの累積挙動を前提に設計する。完了/成功後は ark-ui 側の `api.clearFiles()`（または個別に `api.deleteFile(file)`）で内部リストも空にする。`api` へは `FileUpload.Context` または `useFileUpload` でアクセスする
- ファイル単位の状態は再試行時にも同一ファイルへ正しく対応づける必要がある。File の識別キー（例：`name` + `lastModified` + `size`）を決めて状態と紐づける
- ファイルごとの状態を独立して更新するため、`Promise.all` で一括完了を待つのではなく、各ファイルの Promise が自身の状態を更新する形にする（並列実行は維持）
- フック・state・イベントハンドラを持つコンポーネント（新設ラッパー、`ImageUploadButton`、再試行ボタン）は `'use client'` とする。props を受け取って表示するだけの状態バッジ・サマリ等には付与しない
- エリア全体ドロップは、`page.tsx` の 2 つの `FileUpload.Root` を 1 つに統合して実現する。ボタン・状況リスト・サマリ・ドロップゾーン・ギャラリー (`Images`) を単一の `FileUpload.Root` 配下に置き、ファイルの受理状態を 1 か所に集約する。`page.tsx` はサーバーコンポーネントなので、統合した `FileUpload.Root` を持つクライアントコンポーネントを新設し、`<Images />` は children として渡す（`Images` 自体は `FileUpload` のコンテキストに依存していないため children 化で破綻しない）。ドラッグ中のハイライトは ark-ui の `Dropzone` / data 属性で表現する
- 状況リスト・サマリ・状態バッジは `features/album/components/` 配下に表示用コンポーネントとして切り出す（既存のコンポーネント分割粒度に合わせる）
- 状態の型（`image-upload-status.ts`）はファイル単位の状態（`queued` / `uploading` / `success` / `error`）を表現できるよう拡張する。既存の集約 `status` を使う箇所がなくなる場合は削除する（デッドコードを残さない）
- テストは Jest + Testing Library。コンポーネントには Storybook の story を用意する既存慣習に合わせる

## 決定事項

ドロップアップロードの範囲：Drive / Dropbox 同様、コンテンツ領域（アップロードボタン＋ギャラリー）のどこにドロップしてもアップロードする方針とした（AC-5）。これに伴い `page.tsx` の 2 つの `FileUpload.Root` を 1 つに統合する。
